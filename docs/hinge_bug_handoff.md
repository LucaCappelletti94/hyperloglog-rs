## 2. Bugs found and fixed this session

Both are representation-transition bugs, found by watching the regime benchmark's new `hybrid` modality (the real auto-switching counter) cross its transition points. Both bite when operands span DIFFERENT internal representations, which happens for a band of cardinalities around a transition because operands of slightly different sizes (or different value sets) saturate at slightly different points.

### Bug 1: mixed-representation union was about 50 percent wrong (FIXED)

- Location: `src/hash_list.rs`, `union_estimation_from_sorted_iterator_and_counter`. This is the union path for `self` a sorted hash list and `other` HyperLogLog registers (the `(true, false)` and `(false, true)` arms of `estimate_union_cardinality_with_cardinalities` in `src/hyperloglog.rs`).
- Root cause: it seeded the accumulator with `self.harmonic_sum`, but `self` is the hash list, whose `harmonic_sum` field is a repurposed metadata word (a `NEG_INFINITY`-like sentinel), not a real harmonic sum. The union therefore started from garbage. The out-of-range raw estimate was then clamped by `correct_union_estimate` to `max(left, right)`, which for two equal disjoint sets is exactly half the true union, hence the ~50 percent.
- Fix: seed from `other.harmonic_sum` (the registers operand, which has a real sum), then raise it where a hash in `self` decodes to a higher register rank than `other` holds. One line.
- Verification: a split diagnostic measured mixed-pair union error dropping from ~50 percent to ~0.7 to 1.2 percent (matching same-representation pairs). It was the union spike the hybrid showed at the hash-list to registers transition, and the bulk of the joint sketch's 88 percent spike (the sketch calls this union internally).

### Bug 2: mixed-shell joint sketch had a residual bump (FIXED)

- Location: `src/sketches.rs`, the default `HyperSpheresSketch::joint_sketch` used by plain `HyperLogLog`.
- Root cause: a `JointSketch`'s nested shells are different sizes (the inner shells hold `3 * card` values, the outer `6 * card` in the benchmark), so near saturation the outer shells convert to registers while the inner shells are still hash lists. The differential decomposition then subtracts cell estimates that come from different representations (near-exact hash-list ones and noisy register ones), and the mismatch does not cancel, it amplifies into a bump (88 percent before Bug 1, ~7 percent after Bug 1, versus ~4.4 percent for the all-registers case, at cardinality 1847 for `Precision12, Bits6`).
- Fix: `HyperLogLog::joint_sketch` now overrides the default to UNIFY the representation. If any operand is dense it materializes them all to registers with `into_hll` first, so every cell is computed consistently. The shared inclusion-exclusion body was extracted into `inclusion_exclusion_joint_sketch`, which both the trait default and the override call. The materialization is a no-op once everything is dense and is skipped entirely while all shells are still hash lists, so the near-exact set-algebra accuracy is preserved in that range.
- Verification: at cardinality 1847 the hybrid sketch went from 7.4 percent to 4.40 percent, matching the all-registers result, so the curve is now monotonic (3.76, then 4.40, then 4.91) with no spike. Where all shells are still hash lists the hybrid keeps ~3.8 percent rather than being forced up to the ~6 percent dense level.

### Bug 3: mixed hash-list and registers union skipped the low-load correction (FIXED)

- Location: `src/hash_list.rs`, `union_estimation_from_sorted_iterator_and_counter` again (the `(true, false)` arm of `estimate_union_cardinality_with_cardinalities`, also reached by the `(false, true)` arm via delegation). This is the SAME mixed hash-list and registers union path as Bug 1, but a second, independent defect in it.
- Root cause: after merging the hash list into the registers' harmonic sum (the element-wise register maximum, which Bug 1 made correct), the function turned that sum into a cardinality with the RAW HyperLogLog formula `ALPHA * m^2 / harmonic_sum` directly, skipping the linear-counting and bias correction that both the single-counter `estimate_cardinality` and the both-registers `(false, false)` union arm apply through `corrected_register_cardinality`. At low union load the raw estimator overshoots enormously (for a true union of 1500 at `Precision12, Bits6` it returned about 3745), and `correct_union_estimate` then clamped that down to `left + right`. The clamp masked the overshoot but discarded the overlap: the union came back as the SUM of the two cardinalities, so it was wrong by exactly the intersection. Disjoint operands looked perfect (sum equals union there), which is why Bug 1's disjoint-pair verification did not catch it, and the error grew with the overlap fraction (about 20 percent at one third overlap, about 33 percent at half overlap).
- Fix: track the union zero-register count alongside the harmonic sum (start from `other.number_of_zero_registers()` and drop one whenever a hash raises a zero register of `other`), then feed both to `corrected_register_cardinality` instead of the raw formula. `corrected_register_cardinality` was made `pub(crate)` so the hash-list module can call it. The mixed union now matches the both-registers union to within register noise across the whole overlap range (the previous 20 to 33 percent spikes are gone).
- How it was found: the new property-based suite `tests/proptest_hinge.rs` (see section 3), specifically the `hash_list_vs_registers_is_representation_independent` property, which oracles every representation combination of two overlapping operands against the exact truth. The `hash x hash` and `registers x registers` combinations passed while `hash x registers` failed, which immediately fingered the mixed path. The throwaway `examples/hinge_union_diag.rs` then printed the same-versus-mixed error across an overlap grid and showed the error equalled the intersection.

### Bug 4: the 2-set union MLE seed skipped linear counting at low load (FIXED)

- Location: `src/mle.rs`, `mle_union_regions_from_registers`, the `estimate` closure passed to `mle_union_regions`. This is the seed that maps the union harmonic sum to a union cardinality, from which the three regions (`left_difference`, `right_difference`, `intersection`) are initialized before the Adam refinement.
- Root cause: the closure replicated only the raw plus bias-correction step (`correct_cardinality` over `ALPHA * m^2 / harmonic_sum`) and IGNORED its zero-register argument, so it skipped linear counting. At low union load almost every union register is zero, exactly where linear counting is the accurate estimator, so the seed (and therefore the union MLE) was badly biased there. This is the same linear-counting omission as Bug 3, in the MLE union rather than the default mixed union. It surfaced as a spike at the smallest cardinalities in the regime benchmark's forced-dense MLE column: at `Precision12, Bits6` the union MLE was about 2.06 percent mean relative error at cardinality 16 versus about 0.47 percent for the default union (about 4.3 times worse), shrinking to parity by cardinality 42 and then beating the default past about 100. The single-counter cardinality MLE was fine throughout (it uses Ertl's secant method, a different path), which localized the defect to the union seed.
- Fix: replace the closure with `Self::corrected_register_cardinality(harmonic_sum, zeros)`, the same correction (linear counting at low load, bias-corrected raw above it) the default register union uses. After the fix the union MLE is uniformly BETTER than the default at every cardinality (about 0.33 percent versus 0.47 percent at cardinality 16, about 0.69 to 0.86 times the default error across the sweep), so the low-cardinality spike is gone. The now-unused `correct_cardinality`, `HYPERLOGLOG_CORRECTION_*` and `FloatOps` imports were dropped from `src/mle.rs`.
- How it was found: rerunning the regime benchmark surfaced the MLE column at small cardinalities (the prior on-disk JSON had only the `hybrid` records, with no MLE, kept per cardinality, masking it). `examples/mle_union_lowload_diag.rs` (kept in the tree) measures the default versus MLE union mean relative error over many trials on forced-dense operands across small cardinalities, and confirmed both the defect and the fix.

### Bug 5: the 2-set union MLE wrongly returned an empty union for ~64 zero registers (FIXED)

- Location: `src/mle/union.rs`, `mle_union_regions`, the early-return "empty union" guard.
- Root cause: the guard read `if union_zeros == 1 << B::NUMBER_OF_BITS { return [0, 0, 0]; }`. The number of REGISTERS is `2^P::EXPONENT` (4096 at `Precision12`), but `2^B::NUMBER_OF_BITS` (64 at `Bits6`) is the number of distinct register VALUES, which only sizes the multiplicity arrays. So the guard meant to fire only for a genuinely empty union (every register zero) instead fired whenever a non-empty union happened to have exactly 64 zero registers, returning a union of zero. The number of zero registers for a union of cardinality `n` over `m` registers is about `m * e^(-n/m)`, which is near 64 for a union around 18000 at `Precision12, Bits6`, so unions in that band intermittently collapsed to zero (a 100 percent error on the unlucky inputs).
- Symptom: a variance SPIKE in the regime benchmark's `union: accuracy` panel for `registers MLE` at cardinality 12111, where the per-trial std jumped to 8.75 percent (versus about 0.6 percent elsewhere). It was a single catastrophic outlier among the 256 trials, not a broad bias. The forced-dense single counter has the same guard via the `M = N = 1` joint sketch path, but `cardinality MLE` did not spike because its expected zero count at the probed cardinalities never sat on 64.
- Fix: compare against the register count, `if union_zeros == 1_u32 << P::EXPONENT`. After the fix the cardinality-12111 trials that returned zero (seeds 65 and 254 in the benchmark's `t + 1` seeding) return the correct ~17500 to 18750, and the worst of 256 trials is a normal 3.7 percent.
- How it was found: the `union: accuracy` band spiked at one cardinality after the trial count was raised to 256 (more trials made the rare outlier land in the sample). `examples/mle_union_outlier_diag.rs` (kept in the tree) replays the benchmark's exact per-trial seeding at the suspect cardinalities and lists the worst trials, which showed two trials returning exactly 0.0. A lib regression test `union_mle_does_not_collapse_to_zero_near_64_zero_registers` (in `src/mle/union.rs`) now sweeps all 256 seeds at cardinality 12111 and asserts the union MLE stays within 10 percent.

### Not a bug (fundamental): the cardinality step at the same transition

The single-counter `estimate_cardinality` error STEPS up at the hash-list to registers transition (about 0.5 percent as a hash list, about 1.1 percent as registers, at `Precision12, Bits6`). This is fundamental, not a bug. Converting a hash list to registers is lossy: the hash list stores the actual truncated hashes and counts them near-exactly, while the registers keep only one number per bucket (the maximum rank over the register array) and discard the per-element hashes, so the estimate necessarily falls back to HyperLogLog's inherent standard error (about 1.6 percent for 4096 registers). The structure converts because the hash list ran out of space, not because registers are more precise. The only way to keep the lower error is to convert later (carry the hash list further), which is a known "transition later" idea (see also `docs` references to the hash-list saturation point `SaturationError::Saturation`).

## 3. How the bugs were found (reusable method)

- The regime benchmark `examples/regime_benchmarks.rs` sweeps cardinality and measures several modalities per task. The key one is `hybrid`: a counter built via `insert_value` that auto-switches `value list` then `hash list` then `registers`. It traces the real path a user sees and makes transition glitches visible as spikes in the per-task accuracy panels.
- When a spike appeared, the decisive diagnostic was a throwaway example that builds the two operands at a FINE cardinality grid around the transition, records `repr(a)` versus `repr(b)`, and splits the error into a same-representation bucket and a mixed-representation bucket. The mixed bucket showing ~50 percent while the same bucket showed ~1 percent localized the bug immediately.
- `examples/linear_counting_diag.rs` (kept in the tree) prints, per cardinality, the crate estimate versus pure linear counting versus the raw estimate, as signed bias and absolute error. It is how we confirmed linear counting itself was correct and the problem was elsewhere.
- The reusable diagnostic is now mechanized as property-based tests in `tests/proptest_hinge.rs` (the `proptest` dev-dependency was added for this). It generates two operands from three disjoint element pools (`only_a`, `shared`, `only_b`), so the exact union, intersection, difference and Jaccard are just the pool sizes, then forces each operand into every reachable representation and oracles all of `union`, `intersection`, `jaccard` and `difference` over the full representation cross product against the exact truth. A representation-dependent bug shows up as one combination (typically a mixed one) breaking the tolerance while the same-representation combinations hold. Two properties cover the two transitions: `value_vs_hash_list_is_representation_independent` (small cardinalities, near-exact, tight tolerance) and `hash_list_vs_registers_is_representation_independent` (mid cardinalities, looser tolerance for HyperLogLog's standard error). It is instantiated for `Precision10`, `Precision12` and `Precision14` at `Bits6` via the `hinge_suite!` macro, with per-precision operand-size bands chosen to keep both operands inside the hash list (capacities are roughly `1847 * 2^P / 4096`: about 2100 at P10, 8500 at P12, 34000 at P14). `examples/hinge_union_diag.rs` is the matching same-versus-mixed overlap-grid printer for the hash-list to registers union.

## 4. The hunt for next session: other hinge pain points

The general pattern is: any operation whose result depends on operand REPRESENTATION can fail either transiently at a transition or whenever operands are MIXED. We deeply checked only the hash-list to registers transition for `cardinality`, `union`, and `sketch`. Candidates still to probe:

- The OTHER transition, value list to hash list (around cardinality 217 for `Precision12, Bits6`). Probe `union`, `intersection`, `jaccard`, `difference`, `merge`, and `sketch` with mixed value-list and hash-list operands. This boundary was not stress-tested.
- `intersection`, `jaccard`, `difference`: these are derived from `union` plus the marginal cardinalities (the `CardinalityEstimator` trait), so Bug 1 should help them, but verify there is no separate mixed-representation code path and that they are smooth across both transitions, same versus mixed.
- `merge` / `BitOr`: merging mixed-representation counters (value list against hash list, hash list against registers) goes through the representation matrix in `HyperLogLog::merge` (`src/hyperloglog.rs`). Verify the merged object and its cardinality are correct for every mixed pair, especially right at a transition.
- The hash-list-INTERNAL downsampling. The hash list reduces its `hash_bits` as it fills, and each downsample is a mini-hinge. The hash-list accuracy was seen rising toward saturation. Probe accuracy finely as `hash_bits` steps down to confirm each downsample is smooth and unbiased.
- Value-list-internal growth. The value-list buffer grows by doubling via `increase_capacity`. Probe insert cost and correctness around each capacity doubling.
- MLE near transitions. The `.mle()` path materializes to registers, but verify the joint MLE and the MLE dispatch behave at the boundaries (the MLE dispatch already has a noted near-boundary weak spot).
- `may_contain` and any other cross-representation query.
- Re-verify the `(true, true)` both-hash-list union (the merge-based path) after the Bug 1 harmonic-sum fix, to be sure nothing else read a hash list's `harmonic_sum` field as a real sum. Grep for `.harmonic_sum` reads where the operand might be a hash list or value list.

Concrete plan: generalize the same-versus-mixed split diagnostic from section 3 to ALL the binary operations (`union`, `intersection`, `jaccard`, `difference`, `merge`) at BOTH transitions, over fine cardinality grids, and flag any operation where the mixed bucket is much worse than the same bucket. Then add those operations (and the value-to-hash transition) to the `hybrid` curves in the benchmark so the figure exposes them too.
